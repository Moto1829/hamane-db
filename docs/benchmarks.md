# ベンチマーク記録

## M8: 検索スレッドプール化 (todo 801, 2026-07-15)

環境: Apple Silicon (aarch64) / macOS / release ビルド。
SIFT 200k (dim 128, L2)、セグメント 2 個 (110k + 90k、HNSW あり)、
クエリ 1,000 本、k=10、ef=64、クライアント 1 スレッド。

計測方法: DB 構築はバックグラウンドフラッシュのタイミングでセグメント構成が
run ごとに変わり比較にならないため、**同一 DB** に対し新旧バイナリを
交互に 3 回ずつ (各 3 ラウンド) 実行して比較した。両者の検索結果は
checksum 一致。

| 実装 | QPS (1 thread) | 平均レイテンシ |
|---|---|---|
| thread::scope (検索ごとに生成、503) | 4541〜4655 | 0.217 ms |
| 共有プール (801) | **5201〜5294** | **0.190 ms** |

約 14% のスループット向上 (クエリあたり約 27µs のスレッド生成コストが消えた)。
ディスパッチ単体のマイクロベンチ (150µs のジョブ × 3、うち 1 個は呼び出し
スレッドが実行) でも scope 123µs → プール 78µs。

## M7: SQ8 の u8 SIMD カーネル (todo 701, 2026-07-15)

NEON (aarch64)、dim=768。整数演算のためスカラーと完全一致:

| カーネル | f32 SIMD | SQ8 SIMD | 倍率 |
|---|---|---|---|
| L2 | 90.2 ns | **21.5 ns** | 4.2x |
| dot (+Σb) | 88.7 ns | **23.3 ns** | 3.8x |

完了条件 (f32 SIMD の 2 倍以上) を達成。
u32 アキュムレータのため dim ≤ 66051 が前提。

x86_64 の AVX2 は 2026-09-11 に追加 (todo 701)。**速度は未測定** —
手元に x86_64 の実機が無いため、正しさ (スカラーとの完全一致) のみを
CI (ubuntu = x86_64) で検証している。測れる環境が手に入ったら
同じ criterion ベンチ (`cargo bench -p hamane-core`) で倍率を記録する。

## M5 の改善結果 (2026-07-14)

環境: Apple Silicon (aarch64) / macOS / rustc 1.93.0 / release ビルド。

### HNSW 構築の並列化 (todo 501)

SIFT1M (100 万 × 128 次元)、`cargo run --release -p hamane-bench -- --data data/sift`:

| 構成 | 構築時間 | recall@10 (ef=64) |
|---|---|---|
| M4 (単一スレッド) | 1438.8 s | 0.977 |
| 単一スレッド + HashSet 修正 | 1377.8 s | 0.972 |
| **並列 (auto = 全コア)** | **297.7 s (4.8x)** | **0.972** |

完了条件 (300 秒以内・recall 維持) を達成。`build_threads: 1` のときのみ構築は決定的。

### extendCandidates の計測 (todo 502)

SIFT 200k サブセット、ef=64:

| 構成 | 構築 | recall@10 |
|---|---|---|
| extend ON (既定) | 50.9 s | 0.9897 |
| extend OFF | 40.6 s (−20%) | 0.9881 |
| extend OFF + ef_construction=300 | 44.7 s | 0.9891 |

SIFT のような自然データでは OFF で構築 20% 高速・recall ほぼ同等。
ただし強くクラスタ化したデータでは OFF だと recall が 0.84 まで落ちる
(recall_at_10_clustered テスト) ため、**既定は ON を維持**。
`HnswParams.extend_candidates = false` で opt-out できる。

### バックグラウンドフラッシュ中の書き込みレイテンシ (todo 504)

`cargo run --release -p hamane --example write_latency`
(200k upsert、16MiB 閾値で自動フラッシュを誘発、fsync 除外):

| 指標 | 値 |
|---|---|
| スループット | 141k upsert/s |
| p50 / p99 / p99.9 | 2.6µs / **8µs** / 48µs |
| max | 675ms (backpressure: active が閾値 4 倍到達時のみ) |

完了条件 (フラッシュ中の upsert p99 < 10ms) を達成。M4 まではフラッシュ
(HNSW 構築込み、分単位) の間すべての書き込みが停止していた。

- HNSW 既定パラメータ (m=16, m0=32, ef_construction=200)、単一セグメント

|---|---|
| 挿入 (WAL + memtable) | 3.4 s (298k rec/s) |

| ディスクサイズ | 650 MB (ベクトル 512MB + HNSW ~130MB) |

| ef | recall@10 | QPS (1 thread) | 平均レイテンシ |
|---|---|---|---|

| **64 (既定)** | **0.9772** | **3850** | **0.26 ms** |
| 128 | 0.9939 | 2273 | 0.44 ms |
| 256 | 0.9984 | 1308 | 0.76 ms |

  自然データではオフでも再現率が出る可能性があり、パラメータ化を検討

## M10: 量子化とクラスタリング索引 (todos/1006)

- 日付: 2026-09-03
- 環境: Apple Silicon (aarch64) / macOS / rustc 1.93.0 / release / 単一スレッド
- 実行: `cargo run --release -p hamane-bench -- --limit 200000 --queries 1000 --config <c>`
- 構成: SIFT の先頭 n=200,000 (dim 128, L2)、クエリ 1,000 本、正解は総当たり
- HNSW 既定パラメータ、単一セグメント。PQ は m=32 (dsub=4)、IVF は nlist≈447 (√n)

各構成の代表点 (HNSW 系は ef、IVF 系は nprobe のスイープから recall≈0.99 付近):

| 構成 | 索引 | recall@10 | QPS | 構築 | ディスク |
|---|---|---|---|---|---|
| f32 | HNSW | 0.9894 (ef=64) | 4799 | 32.9 s | 130 MB |
| SQ8 | HNSW + SQ8 | 0.9894 (ef=64) | **9531** | 33.8 s | 154 MB |
| PQ | HNSW + PQ | 0.9835 (ef=64) | 7043 | 89.2 s | 136 MB |
| IVF | IVF | 0.9896 (nprobe=32) | 378 | 31.8 s | **104 MB** |
| IVF-PQ | IVF + 残差PQ | 0.9852 (nprobe=32) | 728 | 86.5 s | 110 MB |

読み取り:

- **量子化 (SQ8/PQ) は HNSW 探索を高速化する。** 1 段目の距離計算が u8/表引きに
  なり、SQ8 で QPS 約 2 倍、PQ で約 1.5 倍。recall は f32 再ランクでほぼ同等
  (SQ8 は完全同等、PQ は僅かに低下)
- **IVF は同 recall で HNSW より遅い** (200k では HNSW グラフの枝刈りが優秀)。
  IVF の価値は構築の単純さと、億件規模でのメモリ特性。IVF-PQ は ADC の表引きで
  IVF 比 QPS 約 2 倍
- **ディスク**: 再ランク用に vectors.bin (512 B/行) を常に残すため、SQ8/PQ は
  量子化ファイルが**加算**されディスクは増える。PQ の圧縮効果 (codes 32 B/行 =
  f32 比 16x) が効くのは「探索時に走査する作業集合」であり、億件規模でこそ意味を
  持つ。IVF は HNSW グラフ (~26 MB) を書かないぶんディスク最小
- 構築時間: PQ / IVF-PQ はコードブック学習 (サブベクトル 32 本 × k-means) が
  加わり f32 の約 2.7 倍。IVF (量子化なし) は粗 k-means のみで f32 と同等

**結論**: 中規模・低レイテンシ重視なら HNSW+SQ8 が最良 (recall 同等・QPS 2倍)。
メモリ制約が支配的な超大規模では PQ / IVF-PQ が作業集合を 16x 圧縮する。
用途に応じて `StoreOptions.{index, quantization, nprobe}` で選択する。

## M11: OPQ (回転付き PQ) (todos/1104)

- 日付: 2026-09-06
- 環境: Apple Silicon (aarch64) / macOS / rustc 1.93.0 / release / 単一スレッド
- 実行: `cargo run --release -p hamane-bench -- --limit 200000 --queries 1000 --config <c> [--rotate-input]`
- 構成: SIFT の先頭 n=200,000 (dim 128, L2)、クエリ 1,000 本、正解は総当たり、
  PQ は m=32 (dsub=4)、単一セグメント

**`--rotate-input`**: base/query に固定の乱数直交回転を掛けてから投入する。
直交変換は距離を保存するので正解は変わらないが、「次元の並びに意味がある」
という構造だけが失われる。多くの埋め込みモデル (次元順に意味がない) を模擬する。

### 素の SIFT (次元順に構造がある)

| 構成 | recall@10 (ef=64) | recall@10 (ef=256) | QPS (ef=64) | 構築 |
|---|---|---|---|---|
| PQ | 0.9838 | 0.9907 | 9446 | 75.4 s |
| OPQ | 0.9832 | 0.9923 | 9420 | 116.1 s |
| IVF-PQ (nprobe=32) | 0.9852 | 0.9943 (nprobe=64) | 792 | 80.2 s |
| IVF-OPQ (nprobe=32) | 0.9832 | 0.9920 (nprobe=64) | 785 | 112.0 s |

### 乱数回転をかけた SIFT (`--rotate-input`、次元順に構造がない)

| 構成 | recall@10 (ef=64) | recall@10 (ef=256) | QPS (ef=64) | 構築 |
|---|---|---|---|---|
| PQ | 0.9584 | 0.9662 | 8895 | 82.1 s |
| **OPQ** | **0.9699** | **0.9761** | 9403 | 110.7 s |

読み取り:

- **SIFT では OPQ の利得はほぼ無い** (recall は誤差範囲、構築は +54%)。SIFT の
  128 次元は「16 空間セル × 8 方位」の並びで、PQ の位置分割 (m=32, dsub=4) が
  この構造に既に合っている。回転で改善する余地が最初からない
- **次元順の構造を壊すと PQ は 2.5 ポイント落ち (0.9838 → 0.9584)、OPQ はその
  半分近くを取り戻す** (0.9699、ef=256 では 0.9761)。**OPQ が効くのは
  「次元の並びに意味がないデータ」** = 多くの埋め込みベクトルがこれに当たる
- **QPS は PQ と同等**。回転は検索ごとに d² の行列ベクトル積 1 回 (dim=128 で
  16k flop) しか増えず、探索全体では誤差
- **構築は +35〜54%**。交互最適化 (16384 行サンプル × 8 反復) と、候補
  (恒等初期値 / 乱数初期値) の比較ぶん。ディスクは opq.bin (dim² × 4 B =
  dim=128 で 64 KB) しか増えない
- IVF-OPQ は素の SIFT では IVF-PQ と同等。粗量子化が先に効くため、残差 PQ の
  回転による差は出にくい

**結論**: 埋め込みモデルの出力のように次元の並びに意味がないデータでは、
`opq: true` を PQ に足すと recall が上がる (構築は 1.5 倍前後)。SIFT のように
次元順に構造があるデータでは利得がないので off のままでよい。学習は
「回転なし」も含めた候補比較で選ぶため、**有効にして素の PQ より悪くなることは
ない** (docs/design/opq.md §1.1)。

補足 1: ef スイープの最初の点 (ef=16) は他より QPS が低く出ることがある。
mmap ページのウォームアップぶんで、recall とは無関係。

補足 2 (todo 1105): 交互最適化の第 2 候補を乱数直交行列からパラメトリック初期値
(PCA + 固有値割り当て) に替えた結果、recall は同等 (回転入力 ef=64 で 0.9697 vs
0.9699、素の SIFT で 0.9831 vs 0.9832) で**構築が約 5% 短縮** (110.7 s → 106.3 s)。
上表の数値は乱数初期値版の計測だが、recall の差は誤差範囲。

## M12: 4-bit PQ サブコード (todos/1203)

- 日付: 2026-09-06
- 環境: Apple Silicon (aarch64) / macOS / rustc 1.93.0 / release / 単一スレッド
- 実行: `cargo run --release -p hamane-bench -- --limit 200000 --queries 1000 --config pq --pq-m <m> --pq-nbits <4|8>`
- 構成: SIFT の先頭 n=200,000 (dim 128, L2)、クエリ 1,000 本、正解は総当たり

| 構成 | コード長/行 | recall@10 (ef=64) | recall@10 (ef=256) | QPS (ef=64) | 構築 | ディスク |
|---|---|---|---|---|---|---|
| m=32, 8bit (既定) | 32 B | 0.9838 | 0.9909 | 9402 | 76.0 s | 136 MB |
| **m=64, 4bit** | 32 B | **0.9863** | **0.9932** | **9492** | **32.7 s** | 136 MB |
| m=32, 4bit | 16 B | 0.9073 | 0.9080 | **12012** | 32.0 s | 133 MB |

(4bit は合成 LUT 版 = todo 1204 の数値。合成前は m=64 で QPS 6391、
m=32 で 8835 だった)

読み取り:

- **同じコード長なら 4bit × m 2 倍が全面的に有利**。recall は 8bit をわずかに
  上回り (0.9863 vs 0.9838)、QPS も同等 (9492 vs 9402)、そして**構築は 2.3 倍
  速い** (32.7 s vs 76.0 s)。k-means のセントロイドが 256 → 16 に減るコスト削減
  (16x) が、m を 2 倍にする増加 (2x) を大きく上回るため
- **合成 LUT (todo 1204) が QPS を取り戻した**。素直に実装すると 4bit は
  1 行あたりの表引きが 32 → 64 回に増えニブル展開も入るため QPS が 3 割落ちる
  (6391)。4bit は 1 バイトに 2 サブコードが入るので、**バイト値をそのまま引く
  `(m/2) × 256` の合成表**を作れば表引きは 32 回に戻り、展開も消える。
  結果 9492 と 8bit 同等になった (recall は不変 = 純粋な高速化)
- コードを半分にする構成 (m=32, 4bit) は QPS 12012 と最速。1 行 16 バイトで
  作業集合が最小
- **コードを半分にする (m 据え置きで 4bit) と recall は 0.907 まで落ちる**。
  しかも ef を上げても改善しない (0.9073 → 0.9081) = 律速は 1 段目の粗さで、
  グラフ探索ではない。メモリが最優先の場合の選択肢
- 4bit の再ランク候補は `k×8` (8bit は `k×4`)。この広げ方が無いと
  m 据え置き 4bit は dim=16 の合成データで 0.685 まで落ちる (docs/design/quantization.md §8.3)

**結論**: PQ を使うなら `pq_nbits: 4` + `m` 2 倍が最良 (同メモリで recall・QPS は
8bit 同等以上、構築 2.3 倍速)。メモリ最優先なら m 据え置きの 4bit が
16 B/行・QPS 12012 で、recall を 7 ポイント譲る。
